## 2. 弹窗压测

脚本：`scripts/stress_dialogs.py`

每个弹窗在独立子进程里执行（超时 60s）：

1. **round 1/2**：构造 → `show()` → 在它上面再弹一个 `fly_message` 提示框（验证模态层叠）
   → 关掉提示框 → `reject()`；要求 `reject()` 在 0.5s 内返回、窗口不可见、无残留模态、
   父窗口没有被永久禁用。
2. **round 3**：向所有 `*_thread` 属性注入一个「isRunning() == True」的假线程 → `reject()`；
   要求不阻塞；随后把假线程标记为结束，要求弹窗自动收尾（或再次 reject 后正常关闭）。
3. 子进程 stderr 扫描崩溃/线程销毁类关键字。

覆盖的 58 个弹窗包括：新增类（角色/地图/事件/任务/称号/名牌/奖励/名牌/舞台/系统语音/伙伴）、
合成类（头像 5 个分段、称号贴图、称号 PJSK、系统语音预览、图片裁剪）、下载类
（Swan、PGKO ×3、PJSK Hub ×2、PJSK 谱面）、详情/浏览/选择类、设置/存档/资源导入、以及与
模态关系最密切的 `ToolInstallProgressDialog`、`DetailDialog`。

说明：`ToolInstallProgressDialog` 在运行中**故意拒绝 Esc**（这是既有设计，见
`test_fluent_modal_safety.py`）；测试确认它可以通过官方 `dismiss_tool_install_progress()`
正常关闭，不算卡死。

## 3. 主窗口页面切换压测

脚本：`scripts/test_page_switch.py`

- 真实构造 `MainWindow` + `deferred_build_ui()`；
- 3 轮遍历全部导航项（角色/地图/歌曲/装扮/背景/称号/名牌/其他）、「其他」8 个分段、
  装扮 5 个分段、设置页；
- 每轮之后检查：无残留模态、主窗口未被禁用；
- 端到端「新增 → 伙伴」「新增 → 角色」：定时器关闭弹窗，验证 `_on_add()` 能正常返回
  （回归 `self._game_root` 的 AttributeError）。

实测（native Windows）：

| 动作 | 耗时 |
|------|------|
| 新增 → 角色（打开 + 关闭） | 1.22s |
| 新增 → 伙伴（打开 + 关闭） | 1.20s |

| 其余分类切换 | ≤ 0.30s |

`_run_all` 共 68 次切换，无一次超过 8s 预算，无残留模态。

## 4. 历史高危链路复现

脚本：`scripts/test_ui_flows.py`（native Windows 下运行）

| 场景 | 做法 | 结果 |
|------|------|------|
| 嵌套 DDS 进度框 | 在已打开的弹窗里调用真实 `run_bc3_jobs_with_progress`（quicktex 真编码）3 次 | 每次正常返回，宿主弹窗未被 disabled，无残留模态 |
| **新建角色 → 点「生成并写入 ACUS」** | `QTest.mouseClick` 真实点击按钮，真实 DDS 编码 + 真实 XML 落盘（临时 ACUS） | `finished == Accepted`，生成 3 个 DDS + `Chara.xml`，无残留模态 |
| 三层模态嵌套 | 外层 → 中层 → 内层依次 `open()`，按内→中→外关闭 | `activeModalWidget` 逐层回退正确，全部关闭后为 None |
| 提示框排队 | 连续两次 `fly_message` | 串行出现、可逐个关闭，无第三条残留 |
| **父窗 disabled 时弹提示框** | `host.setEnabled(False)` → `fly_message` / `fly_question` | 提示框可点击关闭；同步确认框正常返回，无卡死 |
| 反复开关 40 次 | `DetailDialog` × 40 | 顶层窗口数量回到基线，无泄漏 |

「父窗 disabled 再弹框」正是 `fluent_dialogs.py` 里那批 `_release_qt_input_grabs` /
`_ensure_enabled_for_dialog_parent` 补丁要处理的场景，本次实测没有再出现「看得见点不了」。

### 4.1 多层弹窗链（A 唤起 B、B 唤起 C …）

脚本：`scripts/test_dialog_chains.py`。按真实父子关系逐层 `open()`，每层都检查
`activeModalWidget` 是否指向最内层，然后分别用 **内→外**、**外→内**、**中间先** 三种顺序关闭。

## 5. 已知局限

1. **不是人工连续操作**：关闭动作是程序化 `reject()/close()` 或 `QTest` 单点点击，
   没有覆盖「鼠标按住 + 弹窗弹出 + 系统输入捕获」这种原生时序。
2. **网络被替换成立即失败**：验证的是弹窗生命周期，不是真实慢网下的下载体验；
   由于关闭路径已改为不等待，网络慢不再会挡住 UI。
3. **DDS 用 quicktex 编码**，没有调用 compressonator CLI（结果同为 BC3 DDS）。
4. **未在打包后的 exe 上跑**，仅开发环境。
5. 测试给构造函数喂的是最小可用数据（空列表/空 dict），覆盖的是窗口与事件循环行为，
   不是每项业务的正确性。

---

## 6. 结论

- 58 个弹窗、68 次页面切换、两条历史高危链路，在两套 Qt 平台上均**没有出现**卡死、
  超时、崩溃或残留模态。
- 之前的 `self._game_root` 崩溃入口已由「新增 → 伙伴」端到端测试覆盖。
- 「新建角色 → 确定」当前走真实点击 + 真实 DDS + 真实 XML，能正常结束。
- 仍建议人工把这三条路径各点一遍（新建角色、下载中关弹窗、设置页来回切），
  因为原生输入层的「点不动」无法完全由程序化测试替代。
